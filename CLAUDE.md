# vovk monorepo

Workspaces: `packages/vovk` (runtime), `packages/vovk-cli`, `packages/vovk-ajv`, `packages/vovk-python`, `packages/vovk-rust`, plus `docs/` (vovk.dev), `examples/*` (hello-world, kitchen-sink, realtime-kanban, multitenant; each deploys to Vercel) and `perf/`, which run the packages from this repo. `test/` is a separate Next.js app with its own lockfile that consumes all packages and holds the integration tests. `skills/` holds the in-repo task guides.

## Commands

- `npm run build` builds all packages (turbo) and links the `vovk` bin; the apps need it before they build
- `npm run build -w <workspace>` builds one app; docs code fences with `source=` sync from the repo files via `npm run update-mdx-github-codeblocks -w vovk.dev`
- `npm t` runs everything: lint (biome), build, unit and integration suites, CLI specs
- The yarn, bun and pnpm cases of the `vovk init` spec run only with `VOVK_TEST_ALL_PACKAGE_MANAGERS=1`; CI sets it nightly
- `npm run test:main` generates the client, typechecks and runs the test app suites

## Conventions

- Conventional commits: `fix(scope): subject`. Git tags are per package: `vovk-v3.7.0`, `vovk-cli-v0.2.0`.
- Each package ships its `CHANGELOG.md` in the tarball; it is the only changelog. The GitHub Release that `publish.yml` makes per tag only links to it and carries the npm provenance. Entries are noteworthy changes only, one short line each, linked to the PR or commit. They are written on request when preparing a release, not per commit and not by tooling; do not add entries unprompted.
- Generated files start with the `Generated by vovk-cli` first-line banner (`packages/vovk-cli/src/utils/generated-banner.mts`). The pruner keys on it, so every new non-JSON template must emit it on line 1.

## Hard rules

- Releases go through tags. `PACKAGE=<name> npm run <type>` (`patch`, `minor`, `major`, `beta`, `beta-minor`, `beta-major`) checks, builds, bumps the version, commits, pushes, then pushes the `<name>-v<version>` tag. The tag runs `.github/workflows/publish.yml`, which publishes to npm once CI passes on that commit. `-- --dry-run` checks and prints the plan only.
- A release happens only when the owner says so, every time; never on an agent's own initiative. Never run `npm publish`: each package's `prepublishOnly` refuses it outside GitHub Actions.
- Only the release script edits `version` fields; it also moves the apps' ranges on the released package. Never edit the published packages' peer ranges.
- Lockfiles: plain `npm install` only, never `--legacy-peer-deps` (it strips next's peer react entries from the root lockfile and breaks `npm ci`). After dependency changes verify with `npm ci --dry-run` on npm 10 and npm 11, at the root and in `test/`.
